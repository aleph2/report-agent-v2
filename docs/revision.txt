Running a whole case in two stages

  python -m reportagent stage1 CASE --max-tokens 300000 --phase-cap clarify=60000
  python -m reportagent stage2 CASE --max-tokens 300000 --phase-cap revise=220000
  Both stages accept repeated --section NAME to run only named sections in existing plan order, sharing one cap per invocation.

Stage 1 ingests and plans the case, then runs gather, write, verify-sources,
review and clarify for each section before exporting the draft and client sheet.
For stage 2, put the answered workbook back in CASE/out/<xlsx_file> with its
original headers and question numbers. Numbered text answers in cfg.answers_file
take precedence for the same question. Each section receives all nonempty numbered
answers in question order, including answers recorded under other sections or
without a section label. A changed answer reopens revision for each selected
section. Stage 2 revises the selected sections and exports.

Each invocation has one shared --max-tokens allowance. Repeat --phase-cap NAME=N
for distinct model phases in that stage. Each override replaces the phase default
in every section, up to the remaining allowance. Plan and write default to the
remaining allowance and gather defaults to 60% of it. The four revision defaults
are listed below. The first line of each invocation in work/runs/progress.txt and
stdout lists the shared cap and effective phase limits at the start. The allowance
is recalculated before each phase. A restart skips completed work on disk.

Revision of one existing section

First refresh its mechanical source-page list (offline):
  python -m reportagent check CASE --section NAME
With a separately authorised live-run budget:
  python -m reportagent revise CASE --section NAME --max-tokens 300000
NAME is the section file stem, including spaces and Chinese characters if present.

To reuse the existing verification and review, select the remaining phases and their caps:
  python -m reportagent revise CASE --section NAME --max-tokens 300000 --phases clarify,revise --phase-cap clarify=60000 --phase-cap revise=220000
--phases selects a comma-separated subset in workflow order. Repeat --phase-cap NAME=N
for distinct selected phases. Each effective cap is limited by the remaining total.
Clarify receives the next free clarification number (highest recorded plus one, or 1
in an empty case) and each conflicting record with its file and line. Its first
message also includes this section's F/grade discrepancy lines from the latest check.

Default phases and caps: verify-sources (80k), review (100k), clarify (40k),
revise (80k). Each cap is also limited by the remaining CLI budget; unused
allocation cannot increase another phase's maximum. Usage is counted after
responses, so a single response can still cross a cap, as in other commands.

verify-sources receives the check file's top source list as its first message,
then saves work/reviews/NAME-sources.md. review uses that note and saves
work/reviews/NAME.md. clarify completes work/clarifications/NAME.md, then
revise edits work/sections/NAME.md. Packaged phase skills are preloaded.
Clarify starts with the review, section, official clarification file, pending drafts
for this section (NAME.pending.md and NAME.pending.*.md), owner answers,
and full records for duplicate numbers. Its final save targets the official file.
Review starts with the numbered section, its source check (or a missing-file note),
official clarifications, owner answers and section notes. Revise receives the same
inputs with the section review in place of its source check.
Line numbers followed by a tab are display prefixes and are excluded from edits.
Only revise enables the model to return several tool calls in one response.
A response consisting of multiple edit_file calls is dispatched one native edit
at a time in order. Each result is retained, including a failed match. After
the batch, the original response and its tool results form the next model input
and the saved transcript. Model usage is counted once per provider response.
The four revision phases use the tool settings described below.

Each phase saves its full transcript in work/runs/. Standalone review runs only
the review phase. plan/run, including --write-only, are for initial drafting;
use revise for the four-phase revision workflow. No file-content judgement or
quality gate is added: the agents still decide what evidence and prose mean.

Every model-taking command (plan, run, review and revise) checks the remaining
phase and total allowance before each request. If estimated input plus the output
reserve exceeds the effective allowance, the phase ends locally. The reserve is
24,000 for verify-sources, clarify and revise, 16,000 for review, and 8,000 for
other phases. phase-settings.toml holds the four phase reserves and thinking
budgets. For a supporting Bailian model, set THINKING_BUDGET_MODEL in .env to its
exact model ID. Only calls to that model in those four phases send thinking_budget.
An admitted request limits max_completion_tokens to the allowance less estimated
input. After a response reporting input usage, the next turn requests a final
save when the remaining allowance falls below twice the previous reported input
plus twice the phase reserve. This last request offers only edit_file for revise
or write_file for any other phase. Admission still prices the normal tool set.
The offline revise --preflight output includes conservative_floor_3, three times
the estimated first input plus three output reserves. Later tool results can
increase input beyond that estimate.
The guard and request log are always enabled. Each decision is appended before
transport to work/runs/<timestamp>-<phase>.requests.jsonl, with estimated input,
remaining tokens, reserve, maximum output and send/stop decision. A response
event with the same request number records reported input, output, reasoning
and total tokens. Null means the provider omitted the field. A stopped or
unanswered send has no provider response event. The estimate includes
the assembled system and chat messages, tool schemas and images. LangChain uses
1.5 characters per token and 16,384 tokens per image here. Provider tokenization,
image handling and unreported usage can affect accuracy.

Phase tool settings

All four revision phases default to tool_policy = "restricted" in phase-settings.toml.
Each may read /index.md to map cited pages to /sources/ and use read_file under /sources/. Verify-sources and review use write_file
only for their own work/reviews/NAME-sources.md and work/reviews/NAME.md files,
respectively. Direct build_agent callers for these phases pass section=NAME.
Clarify uses write_file and revise uses edit_file. Disallowed calls
return a tool error. The first message lists files included in full, including any
source pages attached for verification. A refused read repeats that list when
available. Case launchers that attach whole files should add their case-relative
paths to the first message’s supplied_files metadata. Excerpts and unavailable
files are omitted. Older frozen messages
without a delivery record receive general path guidance. Omitting tool_policy restores the full tool set in that phase.
For clarify and revise, "force-first" uses all tools and requests the phase's named
write or edit on its first request. On Bailian that request disables thinking
and omits thinking_budget. Later requests use their usual model settings.
Provider documentation: https://help.aliyun.com/zh/model-studio/qwen-function-calling

Offline score arithmetic

  python -m reportagent check CASE --score-arithmetic [--section NAME]

This read-only mode prints discrepancies to stdout. Omitting NAME checks every
section file. With checks.score_arithmetic = true, the regular section check also
prints the arithmetic diagnostics. Its existing checklist contents are unchanged.
The setting defaults to true. The check multiplies the adopted R by its weight
in each indicator row, including an explicitly specified baseline midpoint. An
unresolved score or weight makes that table unavailable for comparison. The check
compares the baseline with the calculation and conclusion; alternative scenarios
and interval endpoints have separate meanings. Absolute score differences greater
than 0.01 and grade differences are reported. Table 3-3 boundaries are 30, 45 and
60, with equality in the lower grade. This checks consistency of recorded numbers.
